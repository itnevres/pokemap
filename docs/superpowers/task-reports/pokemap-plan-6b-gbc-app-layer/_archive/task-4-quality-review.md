## Findings

### Important

**1. The "page scrolls horizontally while hovering" observation is not actually resolved -- the implementer's dismissal is unverified.** (`packages/ui/src/styles.css:635-649` `.map-canvas__status`; `packages/ui/src/gbc/GbcMapCanvas.tsx:431-449` status strip; `docs/.../task-4-implementer.md:120` "an artifact of Playwright auto-scrolling... not an app defect")

The reused `.map-canvas__status` rule (`overflow: hidden; white-space: nowrap;`, pre-existing GBA CSS, unmodified by this task) is now carrying **much longer** content than any GBA hover string ever produced: `(bx,by) step (sx,sy) id 0x.. [renders as border 0x..] · TL <name> <category> [+talk] · TR ... · BL ... · BR ...` plus one `· <kind> #<index> <label>` per event at that step -- routinely 150-250+ characters, monospace, at a narrow window this can genuinely exceed the available width. Neither `.map-canvas`, `.app__canvas`, nor `.app__map-editing-body` sets an explicit `min-width: 0`; the "no ancestor overflow" behaviour currently relies entirely on the flexbox spec's automatic-minimum-size-is-0-for-scroll-containers rule applying transitively up through `.map-canvas__status`'s own `overflow: hidden`, which is correct in the common case but is not the kind of guarantee this file should be resting on silently.

The implementer's report screenshots this exact symptom (`task-4-newbarktown-hover-building.png`/`-hover-warp.png`, "the browser window is scrolled a few px left") and attributes it entirely to Playwright's own scroll-into-view behaviour on `mouseMove`, with no targeted check (no `document.documentElement.scrollWidth <= window.innerWidth` assertion, no repro via CDP-level pointer dispatch that bypasses Playwright's auto-scroll, no test at a deliberately narrow viewport). Given a human coordinator separately reported seeing real page-level horizontal scroll while hovering, treating the implementer's own screenshot-based explanation as settled is exactly the kind of "reviewer trusts the narrative instead of re-deriving it" gap RESUME repeatedly warns about.

**Fix:** re-verify live at a narrow window width (e.g. 900px) hovering the longest realistic status line (a wall/door quadrant block plus a warp event), with a script-level `scrollWidth`/`clientWidth` assertion, not a visual screenshot check alone. Independent of the outcome, add `min-width: 0` to `.map-canvas` (and/or `.app__map-editing-body`'s children) -- a one-line, zero-visual-risk hardening that removes reliance on the transitive scroll-container inference and directly benefits Task 5/6's `GbcWorldCanvas`, which will sit in the same flex row and is likely to run at least as tight on horizontal space.

### Minor

**2. Hover-status text formatting is not a pure, directly-tested helper, unlike the coordinate math right next to it.** (`packages/ui/src/gbc/GbcMapCanvas.tsx:71-77` `shortCollisionName`, `:347-353` `quadrantLabel`)

`clientToStep` and `parseColorToken` are correctly extracted as pure, exported, unit-tested functions (`GbcMapCanvas.test.tsx:123-148`) -- exactly the "pure helpers preferred over DOM-heavy tests" pattern this project wants. `quadrantLabel`/`shortCollisionName` (the string assembly for `TL WALL wall`, the `+talk` suffix, the `land`-omits-category rule, the hex fallback when `name` is `null`) are private and only exercised indirectly through 3 full mount+`fireEvent.mouseMove`+canvas-stub tests. This is the more string-format-sensitive half of the status strip (spec explicitly calls out several formatting rules: omit category for land, hex fallback for a null name, `+talk` suffix), and it would be cheap and more discriminating to pull it out as an exported pure function (e.g. `formatQuadrant(key, label, info, hovered): string`) with a table-driven unit test covering land/wall/water/talk/null-name combinations directly, the same way `overlays.test.ts`'s `fixturePayload` gives every field a distinct value. Not blocking; the current DOM-mount tests do cover the real cases exercised in the live-verify narrative.

**3. `GbcTimeOfDay` is on track to be declared a third time.** (`packages/ui/src/gbc/GbcMapCanvas.tsx:10`, `packages/ui/src/gbc/GbcApp.tsx:9`)

`GbcApp.tsx` declares its own `TimeOfDay` union and `GbcMapCanvas.tsx` redeclares an identical `GbcTimeOfDay` union rather than importing it, with a documented rationale (a leaf canvas shouldn't import a type from the app shell that mounts it). That reasoning is sound for *this* pair, but Task 5's `GbcWorldCanvas` almost certainly needs the same time-of-day type too, which would make a third independent declaration of the same 3-value union. Worth relocating the canonical `GbcTimeOfDay` to a small shared spot (`gbc/model/types.ts` or a new `gbc/time.ts`) now, so Task 5 imports one canonical type instead of adding a fourth copy or awkwardly importing from a sibling leaf component.

**4. `hex()` is now defined independently in 4 places** (`MapCanvas.tsx`, `MetatilePalette.tsx`, `GbcMapCanvas.tsx:69`, `GbcMetatilePalette.tsx:16`) -- all byte-identical one-liners (`` `0x${n.toString(16)}` ``). Consistent with this codebase's existing per-file-duplication convention (not a regression introduced by this task), but a good candidate to consolidate into a shared `ui/src/format.ts`-style helper before Task 5/6 adds a 5th/6th copy for `GbcWorldCanvas`/lenses.

**5. `GbcMetatilePalette`'s grid has no collection-level ARIA role.** (`packages/ui/src/gbc/GbcMetatilePalette.tsx:47-72`)

Each cell has a correct `aria-label="metatile 0x.."`, and the selected one carries `aria-current="true"` (DESIGN.md's own accessibility baseline, matched exactly). But the `.gbc-metatile-palette__grid` container has no `role="list"`/`role="grid"` and the cells are plain `<div>`s with no `role="listitem"` -- a screen reader has no way to announce "N metatiles" as a collection, only N unrelated labeled images in sequence. Since these cells are genuinely non-interactive (no click handler, no tabindex, matching the spec's "read-only" requirement), this is a cheap, low-risk addition rather than a blocking defect.
