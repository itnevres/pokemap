## Important finding

### B1 — Paint completion still does not await the first apply, and drag applies bypass begin

**Location:** `packages/ui/src/gbc/GbcMapCanvas.tsx:608–616,640–649,660–667,688–709`; consequences at `packages/server/src/gbcEditRoutes.ts:176–195` and `packages/ui/src/gbc/hooks/useGbcEditSession.ts:111–125`.

The frozen canvas does not actually enforce the begin→apply-completion→end contract described by its race-safety comments. `paintAt` starts `applyPaint`, assigns its promise to `pendingPaintRef`, but returns no promise. The mousedown chain calls `paintAt` without returning/awaiting that apply. A fast mouse-up has already captured the outer begin-chain promise in `endActiveStroke`, so resolving begin also releases end while the apply is still pending. Replacing the ref from inside the begin callback does not change the promise that mouse-up captured.

**Independent static witness S1, not executed:** make `beginStroke` and `applyPaint` independently held promises; issue pencil mousedown and immediate mouse-up; release begin while leaving apply held. The `.then` callback invokes apply and returns `undefined`, allowing the previously registered end continuation to call `endStroke` before apply resolves. Bucket follows the same path. No speculative React behavior or stale closure is needed for this control-flow result.

**Second path in the same finding:** with begin held, a `buttons:1` pencil move to a different block satisfies the mousemove branch because `dragStartRef` is null. It calls `paintAt` immediately, before begin resolves, and replaces the pending begin promise. After begin, different-cell drag applies remain parallel; end awaits only the latest stored apply rather than every request in the stroke. Same-cell deduplication reduces requests but does not serialize them.

The server explicitly accepts arrival-order execution without locking. Apply waits for its request body, while end has no body. If end is processed before the delayed apply, it observes unchanged blocks, clears `strokeStartBlocks` and pushes no paint command. The later apply changes session blocks without updating `isDirty` or adding undo history. The client sequence guard can then reject that older apply response after the newer end response, leaving the UI clean/stale as well. A dirty-exit/project-switch guard may therefore miss this painted state. This is a conditional request-ordering failure derived from source, not a claim that it occurred in the coordinator's live run.

This is **not** a request to add server locking or reopen the accepted generic arrival-order limitation. That limitation's documented intended mitigation is that the client awaits round trips. The actual stroke producer violates that assumption, even for one fast click. The Task 5b static pass covered the newly strengthened invocation-order witness and local visit guard; this broader final pass identifies the missing completion barrier.

**Why existing evidence misses it:** `GbcMapCanvasEdit.test.tsx` delays begin but resolves apply immediately and records invocation order. The strengthened App paint test holds begin but its apply fetch returns immediately; it asserts begin/apply/end calls and exact coordinates, not that end stays absent while apply is held. The drag-dedupe test deliberately waits for the first apply call before moving and does not hold begin. None of these tests distinguishes S1 or a move during pending begin. Earlier mutation kills for omitting the begin/end wait do not prove this stronger ordering requirement.

**Narrow correction/verification target:** make the stroke's promise represent begin and all queued applies, including the first apply; enqueue held-pencil moves behind begin and earlier applies; end only after that chain settles. Preserve map/visit ownership, rect/shift behavior, same-cell dedupe and visible failure handling. One held-begin-plus-move witness and one independently held-apply fast-click witness should establish the missing barrier; a second apply held independently should prove that end cannot outrun an earlier drag apply. This report requests no extra broad suite, and this reviewer has run none. Coordinator decides disposition and any same-implementer continuation.
