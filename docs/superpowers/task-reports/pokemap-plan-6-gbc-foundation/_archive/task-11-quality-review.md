## Strengths

- **The port is faithful and the reuse boundary is right.** `buildGbcWorld` (`packages/core/src/gbc/world/connections.ts:112-177`) mirrors GBA `buildWorld` (`packages/core/src/world/connections.ts:30-119`) structurally — same BFS shape, same `placedBy` tracking for conflict provenance, same shelf-pack call — while genuinely differing where GBC differs (no vertical links, `targetConst` instead of numeric `id`, direct `width`/`height` fields instead of a `layoutById` indirection, and an intentional throw instead of GBA's silent `continue` on an unresolved target, justified with a measured "0 misses in 142 real connections" argument). Given how different the two `Project`/`GbcProject` shapes are, a shared generic BFS core would need a strategy-object abstraction to inject direction sets, target resolution and sizing — plausibly more machinery than the ~30 duplicated lines are worth. The port is the right call, and the type/shelf-pack reuse (`export type { Placement, Bounds, Component, Conflict }; export { boundsOf, layOutComponents };`) is exactly the level of sharing the spec asked for.
- **The GBA edit is minimal and inspectable.** `packages/core/src/world/connections.ts`'s diff is exactly two `export` keywords plus one optional, default-preserving parameter (`opts.gap ?? 8`, `opts.rowTarget ?? 512`); the one GBA call site passes no third argument, so behaviour is unchanged. A GBC-side unit test (`connections.test.ts:245-271`) pins `layOutComponents`'s default-args behaviour directly, which is the right mitigation for not being able to run the GBA suite here.
- **Doc comments are unusually well-grounded.** Nearly every non-obvious choice (offset axis reversal vs. the macro's own source comment, `targetConst` vs `targetName`, the throw-vs-continue divergence from GBA, the `GBC_ROW_TARGET`/`GBC_GAP` reasoning, the `blitScaled` scale-fraction conversion, the bbox exclusion's `<=`/`>=` boundary) cites the specific finding or measurement behind it rather than asserting it.
- **Test quality is high where it's covered.** The hand-derived "+"-shaped fixture (`connections.test.ts:74-233`) builds a real `GbcProject` shape with no unchecked casts, throws loudly from every unused stub method, and asserts placements relative to `Home` rather than absolute coordinates (correctly accounting for the post-BFS shelf-pack shift). The conflict test checks that the two recorded positions actually differ, not just that both exist. The corpus tests pin real, checkable numbers (component membership list, conflict count, reciprocity count) rather than vague assertions.
- **`renderGbcWorld`'s bbox exclusion matches GBA's own render-world exclusion shape exactly** (`p.x + p.width <= bbox.x || p.x >= bbox.x + bbox.w || ...`, same as `packages/cli/src/index.ts:123`), confirmed by direct comparison — good cross-family consistency.

### Important

1. **`GBC_ROW_TARGET`/`GBC_GAP`'s specific values are asserted by doc comment but not tested — confirmed by mutation.** `packages/core/src/gbc/world/connections.ts:65,74,176`. The doc comment gives a real, specific justification (256 must be ≥ Johto's measured 235-block width, or Johto wraps mid-landmass into a messier pack), but no test checks it. I mutated `GBC_ROW_TARGET` to 50 and `GBC_GAP` to 1 in a scratch copy and ran the full gbc/cli suite: **all 35 tests in the affected files stayed green** — the existing "shelf-packs multiple components without overlap" test (`connections.test.ts:218-233`) only checks non-overlap, which the packing algorithm guarantees for *any* positive `rowTarget`/`gap`, so it can't catch this. Nothing in the corpus tests pins the total packed extent (255×746 blocks, per the implementer's own report) or checks that Johto and Kanto land in separate rows. Fix: add a corpus assertion along the lines of `expect(boundsOf([...all placed maps], w.placements)).toEqual({ ... 255, ..., 746 })`, or more targeted, assert Johto's and Kanto's components occupy non-overlapping y-ranges (which a too-small `rowTarget` would break by wrapping Johto into Kanto's row).

2. **The `cmd.getOptionValueSource("scale") === "default"` half of the per-family default check is dead code, and the whole construct is more complex than needed.** `packages/cli/src/index.ts:94`. Since this option no longer has a commander-level default (it was deliberately removed so GBA/GBC could each pick their own), `getOptionValueSource("scale")` can never actually return `"default"` — I verified this directly against the installed commander: with no configured default and `--scale` omitted, it returns `undefined`, not `"default"`. So the check reduces to `opts.scale === undefined ? 8 : opts.scale`, i.e. plain `opts.scale ?? 8` — exactly the same shape already used for GBA two lines down (`index.ts:102`, `opts.scale ?? 4`). I replaced line 94 with `const scale = opts.scale ?? 8;` in a scratch copy, dropped the now-unused `cmd: Command` parameter, and reran the full `gbcCommands.test.ts` suite plus a manual CLI invocation: everything stayed green and the default-8 behaviour was unchanged (`320x72` for a 40×9-block bbox). This directly answers the task's own question ("is the approach clear, are there simpler options") — yes, there is a strictly simpler and equally correct option, and the current code's own risk note (flagging a "future commander upgrade" as a fragility) is about a code path that isn't actually exercised today.

3. **Forward-looking merge note: `runGbaOnly` becomes dead code once this lands on top of the Task 10 fix round.** `packages/cli/src/index.ts:41-45` (this worktree's copy). This worktree branched before the concurrent fix round (`e71de1a`) converted every other GBA-only command from `runGbaOnly(...)` to a `refuseIfGbc` guard clause; that commit's own comment says explicitly that `render-world` (this task) removes `runGbaOnly`'s last caller and the function should go with it. This commit does remove the last caller *in isolation* (it's still used by 8 other commands in this stale base), so there's nothing wrong with this diff by itself — but whoever integrates this onto the fix-round branch should delete the now-unused `runGbaOnly` function and its doc comment (which already anticipates exactly this) rather than leaving it as orphaned dead code. Not a defect in this commit; flagging so it isn't missed at merge time, per the task's explicit ask.

4. **No test exercises the actual default-scale-8 CLI path for GBC.** `packages/cli/test/gbcCommands.test.ts:240-247`. The one dedicated `render-world` e2e spawn test always passes `--scale 32` explicitly; nothing calls `render-world` on the GBC root without `--scale` and checks the output is scaled by 8. I confirmed manually (`npx tsx .../index.ts --project <gbc> render-world --bbox 145,251,40,9 -o out.png` with no `--scale` → `320x72`, i.e. ×8) that the current code is correct, but this is exactly the kind of default-resolution logic (see Important #2) that a regression could silently break without any test noticing. A one-line addition to the existing e2e test (omit `--scale`, assert `40*8 x 9*8`) would close this.

### Minor

5. **`renderGbcWorld` always renders each placement at full native resolution and then downsamples via `blitScaled`, even at scale 8.** `packages/core/src/gbc/render/world.ts:66-75`. This is a real, deliberate, and adequately measured trade-off (0.63s for the entire 391-map corpus at scale 8 vs. 1.49s at scale 32, per the implementer's report) — not a bug — but the source file's own doc comments don't mention that the "cheap" scale-8 case still pays the full per-map render cost; only the task report does. A one-line comment near the `renderGbcMap` call noting this would save a future reader from assuming scale 8 renders are proportionally 4× cheaper at the source-map level too.
6. **`BLOCK_PX = 32` is redefined locally in `render/world.ts:9`** rather than reusing a shared constant, but this matches existing convention: `render/map.ts` has no such named constant either and hardcodes the literal `32` in five places. Not a regression this diff introduces, just an opportunity (shared across both files) that neither the old nor new code takes.
7. **The "de-duplicates defects across multiple drawn maps" test title is slightly broader than what it checks.** `packages/core/test/gbc/render/world.test.ts:100-116`. The test (and its own inline comment) is honest that it verifies two *different* defects from two different maps both surface correctly, not that the *same* defect appearing twice gets collapsed to one entry — the doc comment in `world.ts:26-28` itself says a true duplicate is "unlikely in practice ... but not assumed." Given that, the dedup logic's core claim (two identical `{file, message}` entries collapse to one) has no test at all, hand-derived or otherwise. Low priority since it's genuinely hard to trigger from the real corpus, but a two-line hand-built raster stub (two fake `defects` arrays sharing a `{file, message}` pair) would close it cheaply if this ever needs to be pinned.
