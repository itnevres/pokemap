Every rate, slot, bite-chance, rod-chance and treemon-percent call site in this file is now wrapped, and the fix round closed every previously-unlocated refusal the spec review found (`x.asm:4: SPROUT_TOWER_2F: rate line has 2 argument(s)...`, etc.) — confirmed by the test suite's anchored (`^...$`) regex assertions.
- **`makeWildCursor` correctly builds on `asm.ts`'s `codeLines`** (encounters.ts:98) rather than re-deriving MACRO/ENDM skipping or line splitting — no duplication here despite being a new abstraction not used by any sibling loader.
- **`loadGbcWildData`'s new const-validation pass** (unknown map consts, unknown `TREEMON_SET_*` consts) is a clean, symmetric addition: one loop over `grass`+`water`, one over `treemonMaps`+`rockMonMaps`, both routed through the same `fail`. `wildForMap`'s treemon/rock resolution now throws instead of `?? null`, consistent with the pre-existing unknown-fish-group throw (`resolveTreemonSet`, encounters.ts:583-588).
- **Test pins added in the fix round are well targeted**: the Route35 swarm-vs-base slot diff (M1/M12), the QWILFISH swarm-variant assertion (M2), `wildForMap` actually being exercised on every `FISHGROUP_NONE` map (M8), and the DIGLETTS_CAVE real unequal-rate pin (M10) each correspond to a specific mutation-survivor the spec review found, and each failed when I reverted the corresponding fix (spot-checked M1/M8 by hand).
- Doc comments are generally precise about *why*, not just *what* (e.g. `labelSections`'s comment explains exactly why it can't reuse `labelTail` — local `.dot` labels and stacked-label bodies — rather than silently diverging).

## Issues

### Important

1. **`parseWildProbabilities`'s missing-label error ignores the `file` parameter entirely — the one remaining location-free-and-file-free throw in the fix round's own area of focus.**
   `packages/core/src/gbc/load/encounters.ts:229-233, 241-243`. `labelTailText`'s own `throw new Error(\`no "${label}:" label found\`)` (line 243) is never routed through `fail()`, so it carries neither the file name nor a line number — even though the fix round's entire stated purpose was "every refusal names the file+line" and every other `no "X:" label found` in this same file (`FishGroups`, `TimeFishGroups`, `TreeMons`, lines 352/379/428) already does via `fail(file, null, ...)`. Confirmed live:
   ```
   parseWildProbabilities("WaterMonProbTable:\n\tmon_prob 100, 0\n", "data/wild/probabilities.asm")
   // throws: no "GrassMonProbTable:" label found   <-- no file, despite file being passed in
   ```
   Fix: either wrap the two `labelTailText` calls in `parseWildProbabilities` with `fail`/`at`, or (cleaner, see #2) drop `labelTailText` and use `asm.ts`'s exported `labelTail`, whose own doc already documents that callers are expected to add their own prefix — then wrap that call through `fail(file, null, ...)` on catch, matching the `FishGroups`/`TreeMons` pattern exactly.

2. **`labelTailText` (encounters.ts:241-251) duplicates `asm.ts`'s exported `labelTail` with no documented reason, unlike `labelSections` right below it.**
   `labelSections`'s doc comment (encounters.ts:279-282) explicitly justifies why it can't reuse `labelTail` (local `.dot` labels, stacked labels). `labelTailText` has no such justification, and I confirmed by direct test that `labelTail(text, "GrassMonProbTable")` produces the identical `{text, lineIndex}` shape `labelTailText` does for this file's actual use (plain global labels, no stacking, no local labels needed):
   ```
   labelTail(text, "GrassMonProbTable") // -> {"text":"\tmon_prob 25, 0\n\tmon_prob 50, 1\n\n","offset":19,"lineIndex":1}
   ```
   `cumulativeToPerSlot` only reads `.text`/`.lineIndex`, so switching is a drop-in change (module already imports nothing from `asm.ts` that would conflict; just add `labelTail` to the existing `import { ... } from "./asm.js"` line and delete `labelTailText`). This both removes ~10 lines of duplicate logic and fixes Issue 1 as a side effect once the catch is wrapped in `fail`.

3. **No count/index-completeness check on `GrassMonProbTable`/`WaterMonProbTable`, unlike every other fixed-size table in this file.** `cumulativeToPerSlot` (encounters.ts:253-270) sorts by `mon_prob`'s index argument and diffs consecutive cumulative values, but never checks that the resulting array has the expected length (7 for grass, 3 for water — both already available as `NUM_GRASS_SLOTS`/`NUM_WATER_SLOTS` at the top of the file) or that the indices actually form a contiguous `0..N-1` run. A missing, duplicated, or out-of-range `mon_prob` line silently produces a wrong-length (and, worse, silently-wrong-valued) probabilities array instead of a refusal. Reproduced:
   ```
   // GrassMonProbTable missing index 5 (only 6 of 7 mon_prob lines present)
   parseWildProbabilities(text, "probabilities.asm").grass
   // -> [25, 25, 20, 10, 10, 10]   (length 6, not 7; no error)
   ```
   This is exactly the class of defect the fix round closed everywhere else (`readSlots` now requires exactly 2 args per slot; `parseFishGroups` requires exactly `groupNamesInOrder.length` `fishgroup` lines; `parseTreemonSets` requires exactly `setNamesInOrder.length` pointers) — this one table was missed. Suggested fix: have `parseWildProbabilities` pass the expected count into `cumulativeToPerSlot` (`NUM_GRASS_SLOTS`/`NUM_WATER_SLOTS`) and `fail(file, tail.lineIndex, \`expected ${expected} "mon_prob" lines, found ${entries.length}\`)` when it doesn't match. No test currently exercises this path (`encounters.test.ts`'s `parseWildProbabilities` describe block only tests the happy path and the already-fixed arg-count case).

### Minor

4. **`fail()`'s own doc comment overclaims.** "every refusal in this file goes through this one function" (encounters.ts:44-46) is true for every *data-shape* refusal, but not for `evalPercent`'s intentionally-bare throw (which is separately and correctly documented as such) or `labelTailText`'s missing-label throw (which isn't documented as an exception — see Important #1/#2). Once #1/#2 are fixed this claim becomes true again; until then, it's slightly inaccurate.
5. **`parseGrassFile`/`parseWaterFile` (encounters.ts:139-220) share ~20-25 lines of near-identical block-scanning control flow** (skip blank/end-macro/top-label lines, `db -1` terminator detection, `matchCall(header) ?? matchCall("map_id")`, single-arg check, defect construction) differing only in macro names, rate arity (3 vs 1) and slot shape (3×7 vs 3). This is more structural duplication than the `toWarp`/`toCoord`/`toBg` case `events.ts`'s own quality review explicitly declined to unify (that case was 2-field extraction; this is the whole loop). A shared `scanWildBlocks(text, file, headerMacros, endRe, readBody)` returning `{entries, defects}` would remove the duplication at the cost of one more level of indirection. Judgment call, not blocking — the two functions are short and independently readable as they stand, and the fix round already touched both without introducing drift between them.
6. **`dbLinesIn` (encounters.ts:323-335) hand-splits lines via `body.split(/\r\n|\n/)` instead of building on `asm.ts`'s shared line-splitting** (the private `splitLines` that `codeLines` is built on, which also documents handling a lone trailing `\r` with no `\n`). In practice this is safe here because the result is immediately `.trim()`-ed, which absorbs a stray `\r`, but it's a second, independent re-implementation of "split into lines" in a codebase that otherwise centralizes that logic in `asm.ts` (per that module's own stated goal, asm.ts:6-12). Low priority given the `.trim()` safety net.
7. **Positional trailing `boolean` parameters are unique to this file.** `parseGrassFile(text, file, swarm = false)` / `parseWaterFile(text, file, swarm = false)` and the private `orderedNames(consts, prefix, excludeZero)` are the only boolean-positional-parameter signatures anywhere in `packages/core/src/gbc/load/` (checked all 9 sibling files). Call sites like `parseGrassFile(read(...), "data/wild/swarm_grass.asm", true)` (encounters.ts:521) require checking the signature to know what `true` means. Not wrong, just a minor style outlier; a two-line JSDoc `@param swarm` note (there isn't currently a per-param breakdown, just prose) or splitting into `parseSwarmGrassFile` wrappers would help, but the prose doc comment above the function does already explain the flag, so this is low priority.
8. **Trailing default `file` params are occasionally passed redundantly at their own default value.** `loadGbcWildData` calls e.g. `parseWildProbabilities(read("data/wild/probabilities.asm"), "data/wild/probabilities.asm")` — the second argument is identical to the parameter's own default. Harmless and arguably more explicit/robust to a future default change, just a small readability wrinkle worth a `// deliberately explicit` note if it comes up in review again.

## `wildForMap` efficiency (Task 12 atlas concern)
`wildForMap` (encounters.ts:608-634) does up to 6 linear `Array.prototype.find`s per call, over arrays sized (per the spec review's measured corpus counts) grass ≈96, water ≈62, fishGroups 13, treemonMaps 66, rockMonMaps 4. That's roughly 240 comparisons per map. For Task 12's full 391-map atlas that's ~94k string-equality comparisons total — sub-10ms even pessimistically, and it's a one-shot pass (each map is looked up once, not repeatedly). **Not worth indexing now.** If Task 12's actual usage pattern turns out to call `wildForMap` (or re-derive these lookups) inside a hotter loop — e.g. once per encounter slot rather than once per map — revisit with a `Map<string, GbcGrassEntry[]>`-style index keyed by `mapConst`, matching the `Map<string,...>` index idiom already used in `map.ts`/`palette.ts`/`tileset.ts` (e.g. `groupIndexByLabel`, `blkPathByLabel`, `labelMap`). Building that index now would be premature.
