## Verdict

**Approved. No Critical or Important findings, 8 Minor.** Every helper that replaces old code does exactly what that code did: the same formulas, the same order of floating-point operations, the same identity behaviour and the same defaults. The API fits Tasks 5-8. The Minor findings are doc rot around the wrappers, one dead re-export, one misleading name, two gaps in the tests, and some style unevenness.

## What I re-derived

- **`zoomWorldAboutPivot`**: old GBC code (`clamp(zoom*factor)`, `next === view.zoom` returns `view`, `cx = (px - pan.x)/zoom`, `pan = px - cx*next`, `{...view, zoom, pan}`) vs new code (`view.ts` `zoomAboutPivot` continuous, `screenToSource`, then `r === view ? view : {...view, ...r}`). The arithmetic is the same and the identity rule is the same, so `fitted` survives. NaN, a zero factor and Infinity behave as before: NaN passes through the clamp, and Infinity clamps to max. That is not a regression.
- **`worldZoomBounds(32, z, maxWorldZoom)`** equals GBC `zoomBoundsFor` (`GbcWorldCanvas.tsx:903`), `{1/64, max(maxWorldZoom(32), z)}`. At 16 px it gives `{1/128, ...}`. That differs from GBA's `MIN_ZOOM = 1/64` today, which is intended under P12-4j and lands in Task 8. The GBA `computeFit` wrapper default still pins 1/64..16, as M-d requires. 16/2048 and 32/2048 are exact powers of two, so the `toEqual` checks are exact.
- **`computeFit`/`centredFit`/`jumpFit`** match the deleted code character for character: clamp order, the degenerate guard and the pan expression. Test fixtures I checked by hand: (5,10,100x50) at zoom 4 gives pan (-20, 10). `centredFit` gives (50, -30). The 20x18 jump: z = 668/18 x 0.6 = 22.2667, pan x = 500 - 20z = 54.667, pan y = 334 - 29z = -311.733. The 2000x1000 jump: 0.5 x 0.6 is exact in binary (halving maps the nearest double to the nearest double), and 2000 x 0.3 rounds to exactly 600, so `toEqual({zoom: 0.3, pan: {200, 100}})` is exact, not lucky. A pan of `-0 + positive` is `+0`, so no `-0` lands in an exact comparison.
- **`rectOf`** equals both draw loops (`WorldCanvas.tsx:1321-1322`, `GbcWorldCanvas.tsx:842-843`): `p.x*zoom + pan.x`, with no rounding. **`warpPoint`** with offset 1 equals GBA `(p.x + w.x)*zoom + pan.x` (`WorldCanvas.tsx:1194`). With offset 0.5 it equals `projectGbcWarpPoint`'s `event.x / 2` (`GbcWorldCanvas.tsx:152`), and `*0.5` is exact, the same as `/2`. `worldToScreen` computes `pan + x*zoom`, and IEEE addition is commutative, so the result is the same.
- **`hitPlacement`** equals both `hitTest` loops (`WorldCanvas.tsx:1430-1437`, `GbcWorldCanvas.tsx:921-930`): reverse order, half-open edges. GBA's `sizeOfPlacement` consults `sizeByMap` only when `component === -1`. An adapter that uses `sizeByMap.get(p.map) ?? p` for every placement is equivalent, because a singleton component's bounds are its own placement's size.
- **`fitClusters`/`fitFilter`** reproduce GBA `fitWorld` (`WorldCanvas.tsx:638-689`): the same `componentOf` bounds rule and the same fallbacks. `null` replaces GBA's zero-rect result plus its `width <= 0` guard. The equivalent of GBA's `if (bounds.width <= 0) return` is now "null means no-op".
- **GBC drift, `initialFitBounds` (union of `component.bounds`) vs `fitClusters` (union of member placements):** `buildGbcWorldPayload` (`packages/server/src/gbcRoutes.ts:214-243`) sends `components: world.components` from the cached base world, while `placements` go through `placeNearWarps` + `applySidecar`. With no manual moves of a cluster member the two are identical, since core `boundsOf(maps, placements)` built those bounds from the same base positions. After a member of a multi-map component has been dragged (it is now `manual`, and its `component` index is kept), the old fit still framed the original landmass footprint. `fitClusters` frames where the map is actually drawn. That is the P12-4m reading (GBA's rule on placements), and it is arguably more correct. It has no effect in Task 2: `initialFitBounds` is still the live code until Task 7. See M8.

## Findings

### M1 (Minor): stale and oversized doc on the GBA `computeFit` wrapper
`packages/ui/src/components/WorldCanvas.tsx:263-273`. An 11-line block sits above a one-line body, and its `zoomBounds` paragraph is now false: "GBC's world canvas passes `{ min: 1/64, max: 32 }`". GBC now imports `computeFit` from `canvas/worldView.ts` directly (`GbcWorldCanvas.tsx:6`) and never calls this wrapper. The "Plan 6b Task 5, additive" history and the "every existing call site ... unaffected" text are archaeology. **Fix:** replace the block with two lines, for example: `/** GBA's default-bounds wrapper over canvas/worldView.ts computeFit: MIN_ZOOM/MAX_ZOOM are px per TILE (1/64..16); GBC calls the shared one with its px-per-block bounds. */`.

### M2 (Minor): GBC doc pointers now point at nothing
`packages/ui/src/gbc/GbcWorldCanvas.tsx:114-117` ("see `computeFit`'s own `zoomBounds` doc comment for why GBA's `MAX_ZOOM` ... is the wrong unit") and `:122-125` ("Passed to every `computeFit` call in this file"). The `computeFit` this file calls is now `worldView.ts`'s, whose doc says nothing about units. **Fix:** cut the cross-reference in `:114-117` to "Zoom here is screen px PER BLOCK (32 px native), not per tile". `:122-125` can stay but should drop the GBA comparison, or point at `WorldCanvas.tsx`'s `MIN_ZOOM`/`MAX_ZOOM`.

### M3 (Minor): dead `centredFit` import and re-exports
`packages/ui/src/components/WorldCanvas.tsx:7` and `:282` (`export { centredFit, singletonSizes };`). A grep across `packages/` finds no consumer of `centredFit` or `singletonSizes` from `components/WorldCanvas.js`: GBC now imports them from `worldView.ts`, and no test imports either one. The plan keeps old exports "where a test imports them", and none does. `centredFit` is also imported but never called in the file. **Fix:** delete line 282, and drop `centredFit` from the line-7 import (`singletonSizes` stays imported, since `:587` uses it).

### M4 (Minor): `useSmallTiles` is not a hook but is named like one
`packages/ui/src/canvas/worldView.ts:233-239`. The doc itself says "Not a React hook despite the name". The `use` prefix breaks the rules-of-hooks convention, and the Task 5 draw loop calls it inside an effect callback. There is no eslint in the gate, so nothing fails today, but anyone reading it, or any future lint run, will misread it. GBC already has a name for this predicate, `shouldUseLod` (`GbcWorldCanvas.tsx:261`). **Fix:** rename it to `shouldUseLod(zoom, nativePx)` (or `isSmallTileZoom`), delete the apology line, and update the test import.

### M5 (Minor): `hitPlacement` left edge is not pinned
`packages/ui/test/canvas/worldView.test.ts` (the "half-open rects" test). The `(10,10)` query lands inside `b` either way. The right and bottom edges are pinned by `(15,15)` returning null. No query sits exactly on a placement's `x` or `y`, so the mutation `wx >= p.x` to `wx > p.x` survives every test in this file. The name claims half-open, but only half of it is tested. **Fix:** add `expect(hitPlacement([a], 0, 0)).toBe(a)` and `expect(hitPlacement([a], 10, 5)).toBeNull()`. The first pins the closed left edge, the second the open right edge with no `b` masking it.

### M6 (Minor): the `boundsOf` skip with one zero dimension is unpinned
`worldView.ts:110` `if (width <= 0 || height <= 0) continue;`. Every skip fixture is 0x0, so the mutation `||` to `&&` survives. **Fix:** add a `p("W", 900, 0, 0, 5, -1)` entry to the `boundsOf` fixture. The expected union is unchanged, and the entry fails under `&&`.

### M7 (Minor): style unevenness and duplication with existing types
- `worldView.ts` mixes two voices. The functions written in the conductor style (`componentOf`, `fitClusters`, `fitFilter`, `jumpFit`) explain *why*, densely, like `view.ts`. The Aider-written parts carry JSDoc that restates the code: `worldZoomRange` "min = nativePx * WORLD_SCALE_MIN ...", `rectOf` "Returns { x, y, w, h } in screen px", `warpHit` "Entries must have `sx` and `sy` properties", the `worldToScreen` "(re-export of sourceToScreen)" lines, and the `hitPlacement` doc that repeats its own condition. Parameter lists are also spread over many lines where `view.ts` keeps signatures on one. This has no functional cost. It matters only because this module becomes the shared reference that Tasks 5-8 copy from. **Fix (optional):** drop the restating docs and collapse the short signatures onto one line.
- `WorldRect` (`worldView.ts:27-32`) duplicates core `Bounds` (`core/src/world/connections.ts:5`), which both canvases already import. The local GBC `interface FitResult` (`GbcWorldCanvas.tsx:320-323`) now only types the wrapper and duplicates the exported `FitResult`. Also, `boundsOf` shares its name with core's `boundsOf(maps, placements)`, which has a different signature and is re-exported from `gbc/world/connections.ts`. Whoever writes the Task 7 adapter needs to watch that import. **Fix (optional):** `export type WorldRect = Bounds` (or import `Bounds`), delete the GBC `FitResult` and leave the wrapper's return type inferred, and consider renaming to `placementBounds`.
- Two copies of the "spread the result over the view" logic: `zoomWorldAboutPivot` (`worldView.ts:82-93`) and `useStageZoom`'s `zoomBy` (`canvas/useStage.ts:35-38`). This is harmless, but Task 5 should use one of them for wheel and keyboard alike.

### M8 (Minor, note for Task 7): the GBC first fit changes in two ways
1. **It follows manual moves of cluster members** (see the derivation above). A user who dragged a route out of a landmass gets a wider first fit after Task 7.
2. **With a `mapFilter`, it gains the anchored rule.** GBC today calls `fitAllBounds(scoped)` (`GbcWorldCanvas.tsx:559-560`, `:570`, `:577`). After Task 7 it gets `fitFilter`'s rule.

Both follow from P12-4m. Neither is listed by name among the P12-4m test rebases at plan line 24, which names only the GBC Fit-all tests `:685`, `:1323` and `:2001-2009`. **Fix:** the Task 7 report should name these two behaviour deltas explicitly, along with any GBC test whose fixture moves a cluster member or mixes shelved members into a filter. Nothing to change in Task 2.

## Wrappers: is the exported behaviour the same?
- GBA `computeFit`: the old optional `zoomBounds?` with `?? MIN/MAX` per field is now a default parameter object. It is equivalent for both omission and `undefined`, because the type forbids partial objects. The return type is now inferred as worldView `FitResult`, which has the same structure. Pinned by `WorldCanvas.test.tsx:454-485`, unchanged.
- GBC `zoomWorldAboutPivot`: same defaults (`GBC_ZOOM_BOUNDS`), same identity, `fitted` kept. Pinned by `GbcWorldCanvas.test.tsx:242` and nearby tests.
- GBC `jumpFit`: same defaults (`GBC_ZOOM_BOUNDS`, the local `JUMP_FILL_FRACTION` 0.6, which equals the shared constant). Each wrapper carries a 2-line doc, which is appropriate. Only the GBA wrapper (M1) has a block parked above it.
