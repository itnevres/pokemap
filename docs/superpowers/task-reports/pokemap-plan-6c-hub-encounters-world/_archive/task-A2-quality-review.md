| F1 | Critical | `ProjectSwitcher.tsx:47-58` + `ProjectPicker.tsx:146-150` + `SwitchConfirmDialog.tsx:37-42` | When `ProjectPicker` is used inside `ProjectSwitcher`'s modal and a 409 conflict occurs, `ProjectPicker` returns `<SwitchConfirmDialog/>` as its render output — but that output is still nested inside `ProjectSwitcher`'s own `.warp-modal__backdrop`/`.warp-modal__panel`. `SwitchConfirmDialog` then renders **its own** full `.warp-modal__backdrop`/`.warp-modal__panel` (both `position: fixed; inset: 0`, see `styles.css:1786-1805`), producing two nested fixed backdrops and two simultaneous `role="dialog" aria-modal="true"` elements in the DOM at once. This is exactly the case the spec calls out in bold: *"instead of the picker body (never two stacked backdrops)"* — the "instead of the body" swap only removes the picker's own (backdrop-less) content; it does nothing about the switcher's outer shell the picker is sitting inside. Additionally, neither backdrop's `onKeyDown` calls `stopPropagation`, so pressing Escape while the confirm dialog is showing *inside the switcher* bubbles through both handlers: `SwitchConfirmDialog`'s `onCancel` (correctly returns to the picker) fires, **and** `ProjectSwitcher`'s own `setOpen(false)` also fires on the same keypress, closing the entire switcher modal — the user loses the whole picker, not just the confirm step. This is visually a double-dimmed scrim and functionally a surprising "Escape closes everything" exit no test exercises: `ProjectSwitcher.test.tsx`'s only Escape test presses it against the plain picker (no conflict), and `ProjectPicker.test.tsx`'s 409 tests only render `ProjectPicker` standalone (no wrapping switcher modal), so this path has zero coverage. | Double `position:fixed` scrim stacks visually (extra opacity layering); two simultaneous `aria-modal="true"` dialogs is an accessibility violation (assistive tech can't tell which is "the" modal); Escape's behavior in the nested case is actively wrong (closes two levels on one keypress when the user asked to back out of one). | Give `SwitchConfirmDialog` a "bare" mode (no backdrop/panel of its own) for use inside an already-open modal, and have `ProjectPicker` pass e.g. `bare={!!onClose}` (or just always render un-shelled and let `Root`'s standalone call site supply its own single wrapping backdrop). Simplest fix: hoist the backdrop out of `SwitchConfirmDialog` into its two call sites (`ProjectPicker`'s standalone conflict return gets one; `ProjectSwitcher` doesn't get a second one when the picker is already inside its shell) so exactly one backdrop is ever on screen. Add a test that opens the switcher, triggers a 409, and asserts exactly one `role="dialog"` exists and Escape returns to the picker without closing the switcher. |
| F2 | Minor | `ProjectPicker.tsx:100-114` | The browse-fetch effect has no unmount cleanup (`return () => {...}` is absent) — it relies solely on the request-counter ref to ignore stale responses. `useGuardedFetch.ts` (this same PR touches its doc comment) established a `cancelled` closure flag specifically for "a response that resolves after the caller has unmounted... never calls a stale setter." The ref-counter technique here happens to also cover the ordinary stale-navigation case correctly (confirmed by the discriminating test), but on unmount there's no new effect run to bump the ref, so a resolving fetch after unmount still calls `setBrowseResult`/`setBrowseError` on a torn-down component. | In React 18 this is a silent no-op (no crash, no dev warning), so it's not a functional bug today, but it's an inconsistency against this same file's/PR's own established "every guarded fetch clears itself on unmount" convention, and a future StrictMode/testing-library change could make it noisy. | Add `let cancelled = false; ... return () => { cancelled = true; }` and check it alongside the reqId comparison, or route this fetch through `fetchGuarded` + a small local hook that mirrors `useGuardedFetch`'s cancellation instead of hand-rolling half of it. |
| F3 | Minor | `ProjectPicker.tsx:74` (doc comment) | `openProject`'s own doc comment says the POST is "the one exception" to `useGuardedFetch`/`fetchGuarded`, which is accurate, but `SwitchConfirmDialog`'s doc comment ("never stacked alongside it") and `ProjectPicker`'s conflict-branch comment don't mention the modal-nesting case at all (see F1) — the doc comments assert a correctness property that doesn't hold for the switcher call site. | Misleading comments in exactly the area that has the real bug make it harder for the next reader to trust the "never stacked" claim. | Once F1 is fixed, update these two comments to state the actual invariant (e.g. "callers must never wrap this in their own backdrop already showing" or "this owns the only backdrop in the tree"). |
