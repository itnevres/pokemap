| F1 | Important | `packages/server/src/hub.ts:36-39` (`parentOf`) | On POSIX, `parentOf(dir)` for any `dir` one level below root (e.g. `/home`, `/tmp`, `/Users`) returns `""` instead of `"/"`. Cause: `dirname("/home") === "/"`, then `safeNorm("/")` calls `norm("/")`, whose trailing-slash-strip regex reduces the *entire* string `"/"` to `""` -- the win32 guard (`/^[A-Za-z]:$/`) only restores a Windows drive letter, not the POSIX root. Verified by direct execution: `parentOf("/home") === ""` (reproduced with the exact `norm`/`safeNorm`/`parentOf` bodies via `node`). This is the exact same "`norm` collapses a root to something `readdirSync`/callers mishandle" class of bug the code explicitly guards against for `C:/`, just missed for `/`. | Violates the spec's own contract ("`parent` = `dirname`, normalised the same way; `null` at a drive root / `/`") -- a real root, not null, should come back as `"/"`. Currently self-masked only because `?dir=` (empty string) happens to fall into the "no dir given" branch and re-derives the correct root listing -- i.e. it "works" today only by accident of an unrelated falsy-string check, not because the value is correct. Any client that does `parent === null` to decide whether to show an "up" button, or displays `parent` directly (breadcrumb), gets wrong behavior. No test in `hub.test.ts` catches it because test 4's temp tree is two levels below the OS temp root, and test 6 (win32-only) only exercises the drive-root case. | In `parentOf`, special-case the POSIX-root result the same way win32 drive letters are special-cased, e.g.: `function parentOf(dir) { if (dir === "/" \|\| /^[A-Za-z]:\/$/.test(dir)) return null; const p = safeNorm(dirname(dir)); return p === "" ? "/" : p; }` (or check `dirname(dir) === "/"` directly and return `"/"`). Add a non-win32 test mirroring test 6: browse a temp dir created directly under `/` (or assert on a fixed one-level-deep real path) and check `parent === "/"`. |
